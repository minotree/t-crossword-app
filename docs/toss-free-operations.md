# 토스 무료 운영 점검·이상 증가 대응

확인 날짜: 2026-10-20. 비용·정책 근거는 아래 공식 문서이며, 수치·사용량은 운영 시 조직 Usage 화면의 현재 값으로 다시 확인한다. 이 문서는 실행 절차이며 자동 모니터링·알림·함수 진입 전 방화벽을 설치한 결과가 아니다.

## 무료 범위와 현재 상태

- [Supabase 비용 제어](https://supabase.com/docs/guides/platform/cost-control): Free 사용 중에는 과금하지 않지만 지속적인 한도 초과는 서비스 제한으로 이어질 수 있다. Spend Cap은 Pro 기능이며 Free에서 별도 설정하는 안전장치로 안내하지 않는다. 요금제·유료 부가 기능·Spend Cap 설정은 이번 작업에서 변경하지 않는다.
- [함수 호출량](https://supabase.com/docs/guides/platform/manage-your-usage/edge-function-invocations): Free 포함량은 월 500,000회이며 응답 상태와 무관하게 집계하고 OPTIONS는 제외한다. 인증 실패·429·CORS 403도 이미 함수에 도달한 호출이라 비용/한도 방어 완료로 보지 않는다. 프로젝트가 아니라 조직 사용량과 다른 함수 소비도 함께 본다.
- [전송량](https://supabase.com/docs/guides/platform/manage-your-usage/egress): Free의 uncached/cached 전송량 한도는 각각 5GB다. 현재 앱의 지표 종류와 집계 단위를 화면에서 구분한다. 그림책은 토스 번들 자산이며, 이 프로젝트의 Supabase Storage에서 그림책 전체를 전송하는 구조는 아니다.
- 사용자 제공 마지막 Usage 화면은 2026-10-19 기록에 남아 있다(집계 10/17~11/17, 호출 29/500,000 등). 이후 테스트가 있었으므로 이 수치를 오늘의 잔여량으로 재사용하지 않는다. 이번 작업에서 계정의 최신 Usage/청구 메일/알림 수신 상태는 직접 조회하지 않았다.

## 점검 기준: 프로젝트 운영 기준 제안

출시 초기·집중 테스트 기간에는 하루 2회, 안정화 후 하루 1회 조직 Usage와 함수 지표를 확인한다. 이는 담당자의 수동 점검 주기이며 이 채팅이 종료된 뒤 자동 실행되는 예약 작업이 아니다. Usage 집계 지연을 감안하고 앱의 실제 성공 요청 수와 같다고 가정하지 않는다.

기록할 값: 한국 시간 확인 시각, 집계 기간, 조직 플랜, 함수 누적 호출·최근 증가량, DB 크기, cached/uncached egress, Storage, MAU, 제한/경고 배너. 함수 지표는 401·403·429·5xx 비율과 응답 지연을 집계하되 인증 코드·토큰·정답·사용자 원문 식별자를 기록하지 않는다.

| 기준(토스 강제 정책이 아닌 내부 운영 기준) | 대응 |
| --- | --- |
| 한도 50% 또는 현재 추세로 주기 내 초과 예상 | 점검 빈도 증가, 정상 방문/테스트 요청과 증가량 대조 |
| 70% 또는 평소보다 갑작스러운 증가 | 집중 시험·홍보 유입 확대 중단, 요청 경로·반복 재시도·캐시/번들 다운로드 원인 확인 |
| 85% | 잔여량을 남은 일수로 나눠 하루 허용 소비량 산정, 사용자와 제한/점검 전환 결정 |
| 95% 또는 Supabase 제한 경고·급격한 5xx | 사고 대응으로 전환, 시험 중단, 영향 범위 안내. 유료 전환은 자동 선택하지 않음 |

단일 값이 낮아도 최근 급증과 남은 일수 대비 예측 초과를 먼저 대응한다. DB 크기 등 다른 한도도 같은 비율 기준으로 검토한다. 기록은 확인된 수치만 채우며 빈칸을 추정치로 채우지 않는다. 현재 임계값 알림은 설치하지 않았고 자동 이메일 보장도 하지 않는다. 콘솔 알림·조직 청구 메일 수신 상태는 운영자가 별도로 확인한다.

## 호출량 예산 계산

신규 기기 출제도 서버 등록은 필요하다. 대략적인 1회 방문 기본 인증/잔액 2회 + 판당 `(등록 1 + 실제 힌트 요청 수 + 맞힌 단어 제출 수)` + 추가 잔액 조회/재인증/재시도/오류/점검 호출로 계산한다. 캐시된 판 재시도 역시 HTTP 호출은 소비한다.

예시 가정: 하루 100명 × 1회 방문, 각 2판 × 판당 20개 정답·3회 힌트이면 `100×2 + 200×(1+20+3) = 5,000회/일`, 30일이면 약 150,000회다. 실제 통계나 수용 인원 보장이 아니라 계획용 예시이며 다른 함수·오류·재시도는 별도로 더한다. 최신 잔여량/주기 남은 일수와 비교하고 예상 여유가 없으면 유입·기능 운영 계획을 조정한다.

## 이상 증가 대응 순서

1. 집중 테스트·자동 재시도 도구·예정된 유입 확대를 중단하고 시각·집계/경고·오류율을 기록한다. 정상 사용자 학습·힌트 잔액을 임의 삭제/초기화하지 않는다.
2. 함수 경로별 증가가 `/session`·등록·힌트·정답 중 어디인지 확인한다. 401/403 다수는 탐색/외부 호출 가능성, 429 다수는 반복 요청 가능성으로 분류하되 로그만으로 공격이라고 단정하지 않는다. 실행 중인 시험과 앱 버전 오류도 확인한다.
3. 앱의 무한 반복·짧은 재시도 등 코드 원인이 확인되면 수정·검증하고 승인된 버전으로 배포한다. 현재 gateway의 429 자동 재시도 금지·재인증 1회 상한을 유지한다.
4. 처리량 제한·점검 응답으로 mTLS/DB 부하를 줄이는 변경은 영향과 적용 시간을 설명한 뒤 승인받는다. 이 조치는 함수 호출 집계 자체를 막지 못한다. 프로젝트 중지 같은 조치는 웹·DB에도 영향을 주므로 자동 실행하지 않는다.
5. 월 호출량 자체를 강제로 막아야 한다면 함수 진입 전 차단과 원래 Supabase URL 우회 방지까지 검증해야 한다. 무료 외부 프록시만 덧대거나 CORS를 강화했다고 완료 처리하지 않는다. 기존 토스 자체 세션에 Supabase JWT 검증을 단순 활성화하면 인증이 깨지므로 그렇게 전환하지 않는다.
6. 원인을 수정한 뒤 소량 확인·Usage 추세·사용자 기기 동작을 보고 정상화 여부를 결정한다. 긴급 중단·운영 설정 변경·자격 증명 회전·유료 전환은 사용자 별도 승인 대상이다.

## 아직 남은 것

최신 Usage 확인, 담당자와 점검 주기 확정, 콘솔/이메일 알림 수신 확인, 원래 URL까지 포함한 호출량 강제 차단은 미완료다. 2026-10-20 소규모 합성 데이터 원격 시험 21회와 해당 데이터 정리는 승인 후 완료했다. 운영 절차를 작성한 것과 자동 방어 구축을 구분한다. 요청 수·데이터·정리 결과·미검증 범위는 [원격 검증 기록](toss-remote-verification.md)을 따른다.
