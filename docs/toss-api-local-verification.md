# 토스 API CPU·재시도 로컬 검증 (2026-10-19)

후속 구현: 요청 UUID가 있는 새 판 생성의 스냅샷 재사용을 추가했다. 아래 `/round` 비멱등성은 당시 코드와 현재 ID 없는 호환 경로의 결과다. [최신 구현·운영 미적용 상태](toss-round-idempotency.md)를 함께 확인한다. 아래 CPU 표본은 보존한 소스 해시의 과거 측정이며 새 스냅샷 경로의 측정값이 아니다.

## 결과와 범위

API 회귀 검사 33개, 토스 회귀 검사 41개가 통과했다. 별도 실행한 CPU 측정은 108개의 개별 요청과 6개 요청 묶음이 모두 정상 응답했다. 실행 코드·SQL·의존성은 변경하지 않고 검사와 증거를 추가했다. 원격 호출·함수 배포·운영 DB 변경은 하지 않았다.

| 항목 | 확인 결과 | 검증 한계 |
| --- | --- | --- |
| 같은 힌트 UUID 12개 중첩 제출 | 잔액 10→9, 요청 기록 1개 | PGlite 단일 연결 큐 |
| 같은 위치에 다른 UUID 12개 제출 | 잔액 10→9, 사용 횟수 1 | PGlite 단일 연결 큐 |
| 잔액 1에서 서로 다른 단어 힌트 제출 | 하나만 성공, 나머지 잔액 부족, 최종 0 | 실제 행 잠금 경합 미검증 |
| 최종 정답 12개 중첩 제출 | 보상 +5 한 번, 최종 15, 중복 없는 solved | 실제 다중 연결 미검증 |

PGlite는 실제 마이그레이션 SQL을 실행하지만 한 연결에서 요청을 직렬화한다. `Promise.all` 검사는 중첩 호출을 큐에 넣고 결과를 확인하는 회귀 검사이며 PostgreSQL 여러 연결의 격리·대기·교착 상태를 증명하지 않는다. 응답 유실 검사는 SQL이 완료된 HTTP 응답 본문을 읽지 않고 취소한 뒤 다시 요청한다. 저장소 어댑터는 검사 안에서 SQL을 직접 호출하며 실제 Supabase SDK/PostgREST 통신을 흉내 냈다고 주장하지 않는다.

## 로컬 퍼즐 CPU 측정

- 환경: Node v24.22.0 / pnpm 10.34.7, Windows x64, AMD Ryzen 5 7500F.
- 실제 `createHintHandler`의 `/round`를 호출하고 DB는 가짜 저장소로 대체했다. 본문 읽기·공유 엔진 실행·응답 직렬화/본문 읽기를 측정한다. Node/Vitest 시작·모듈 적재·mTLS·실제 DB·네트워크·Edge 런타임은 제외한다.
- 세 난이도 × 8/10/12 크기 × 학습완료 없음/목록 인덱스 절반/첫 두 항목 제외 전부/전부 × 난수 seed 1/2/3 = 108회다. 거의 전부 완료 시 남은 단어가 난이도·단어 조건에 맞지 않으면 빈 퍼즐도 정상이다. seed는 각 표본마다 재설정하고 명시적인 JIT 예열은 하지 않았다.
- `process.cpuUsage`의 user+system 합계와 `performance.now` 경과 시간을 기록했다. Node 프로세스의 다른 스레드 CPU와 OS 측정 해상도가 포함되므로 CPU 값이 경과 시간보다 클 수도 있다. CPU 수치에 CI 통과 기준을 두지 않았다.
- 최종 측정은 다른 자동 검사와 병행하지 않았다. 일반 PC의 백그라운드 부하를 통제한 실험실 측정은 아니다. 108회 CPU 중앙값 16ms, 관측 표본 95백분위 282ms, 최대 485ms, 최대 경과 488.1ms다. 여러 완료 비율을 합친 통계이므로 통상 이용자의 지연 분포로 해석하지 않는다.

2026-10-19 확인한 [Supabase 공식 실행 제한](https://supabase.com/docs/guides/functions/limits)은 요청당 실제 CPU 2초를 설명한다. 로컬 Node 표본이 이 숫자보다 작다는 사실로 hosted Edge CPU 여유를 보장하지 않는다. 로컬 묶음의 합계 2.562초를 단일 요청의 Edge CPU 제한 초과로 해석해서도 안 된다. 현재 측정만으로 공통 생성 알고리즘을 변경하지 않았다.

## 실행 명령

루트에서 실행했다. 일반 API 테스트에서 CPU 측정 1개는 의도적으로 건너뛰고 아래 별도 명령으로 실행한다. 재측정은 `tmp/toss-puzzle-profile.json`만 갱신하며 보관한 문서의 표본을 자동 덮어쓰지 않는다.

```powershell
pnpm.cmd --filter @t-crossword/toss-api test
pnpm.cmd --filter @t-crossword/toss test
pnpm.cmd --filter @t-crossword/toss-api typecheck
pnpm.cmd --filter @t-crossword/toss typecheck
$env:TOSS_PROFILE = '1'
try {
  pnpm.cmd --filter @t-crossword/toss-api exec vitest run tests/puzzleProfile.test.ts
} finally {
  Remove-Item Env:TOSS_PROFILE
}
git diff --check
```

API 테스트 33개·토스 테스트 41개·두 패키지 타입 검사·별도 프로파일 검사 1개·`git diff --check` 통과. 테스트·문서만 추가했으므로 프로덕션 빌드는 반복하지 않았다. psql·pg_ctl·Docker는 명령 경로에서 발견하지 못했다. 의존성 설치나 비밀 환경 파일 읽기는 하지 않았다.

## 남은 검증과 현재 제한

1. 승인된 테스트 프로젝트/계정을 정한 뒤 실제 PostgreSQL 연결을 둘 이상 사용해 같은 지갑의 힌트·최종 정답을 겹쳐 실행한다. UUID 같음/다름, 같은 위치, 잔액 1, 다른 세션에서 같은 사용자, 다른 판의 차감/보상 경쟁을 포함한다. 실제 최종 잔액·요청 행 수·rewarded·solved와 lock wait/오류를 확인한다. 운영 잔액을 임의로 바꾸지 않는다.
2. 배포 승인 후 hosted Edge에서 난이도·크기별 단일 요청과 소규모 요청 묶음을 확인한다. 원격 요청량을 미리 제한하고 상태·latency·546/504 및 Usage 증가를 확인한다. 현재 함수의 배포 상태·계정 사용량을 이번 작업에서 조회하지 않았다.
3. 테스트 전용 연결 중계에서 서버 commit 뒤 실제 응답 연결을 끊고, 토스 앱으로 같은 힌트 UUID·같은 판의 최종 정답을 재시도한다. 재인증 전후에도 중복 차감/보상이 없는지 실제 기기로 확인한다. 브라우저 모의 검사로 대체하지 않는다.
4. 판 생성에는 요청 ID가 없어 응답 유실 후 재시도하면 새 판이 생긴다. 잔액은 차감하지 않지만 생성 CPU·판 보관량·시간당 60판 제한을 다시 소비한다. 인증 세션 응답 유실도 기존 세션을 자동 복구하지 않는다. 힌트/보상 재시도의 멱등성과 구분한다.
5. 앱 완전 종료 후 진행 판·대기 요청을 복원하는 기능은 현재 범위 밖이다. 무료 호출량 자체를 막는 진입 전 방어와 worker 간 요청 제한도 [무료 운영 문서](toss-free-hosting.md)를 따른 미완료 항목이다.
