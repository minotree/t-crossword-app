# 프로젝트 개발 규칙 · AGENTS.md

> 사용법: 이 파일을 대상 저장소 루트의 `AGENTS.md`로 복사하고 아래 프로젝트 정보·지원 플랫폼·실제 명령을 채운다. 기존 `AGENTS.md`가 있다면 덮어쓰지 않고 규칙을 병합한다. 필요하지 않은 플랫폼과 예시 설정은 제거한다. 자동 탐색을 지원하지 않는 AI 도구에는 이 파일을 명시적으로 로드한다.
>
> pnpm workspace 기반 Web/PWA·Ionic React/Capacitor 하이브리드 앱·토스 미니앱의 독립 개발 경험을 일반화한 템플릿이다. 특정 버전·앱 ID·광고 ID·도메인·서비스 규칙을 다른 프로젝트에 그대로 적용하지 않는다.

## 1. 프로젝트 정보

| 항목 | 대상 프로젝트에서 작성 |
| --- | --- |
| 프로젝트 이름 / 패키지 scope | `<project-name>` / `@<scope>` |
| 서비스 목표·핵심 사용자 흐름 | `<service-goal>` |
| 보고 언어 | 한국어 |
| 지원 플랫폼·개발 순서 | `<예: Web/PWA → Android → Toss → iOS>` |
| 현재 구현·배포 상태 | `<플랫폼별 완료/준비/미구현>` |
| 백엔드·인증·호스팅 | `<선택한 서비스와 책임 범위>` |
| Node / pnpm | `<engines 및 실제 설치 버전>` |
| 업로드·검토 요청·출시 담당 | `<사용자/에이전트 및 승인 범위>` |
| 요구사항 / 진행 기록 | `<실제 문서 경로>` |

미결정 항목은 추측해 운영 설정으로 확정하지 않는다. 관련 없는 작업은 진행하고, 구현·보안·출시에 영향을 주는 필수 결정만 질문한다.

## 2. 변경하지 않는 설계 원칙

1. **도메인·업무 규칙·검증·재사용 가능한 데이터 접근은 공유하고, UI와 라우팅은 플랫폼별로 소유한다.**
2. 각 앱은 화면·스타일·탐색·플랫폼 SDK·인증 초기화·네이티브 연동을 소유하고 독립 빌드·배포할 수 있어야 한다.
3. 공유 코드는 가능한 한 React와 플랫폼 SDK에 의존하지 않는 순수 TypeScript로 유지한다.
4. 작은 일관된 변경을 우선한다. 사전 승인이 없는 공유 UI 패키지·공유 라우터·과도한 추상화를 만들지 않는다.
5. 웹 화면이 동작한다는 이유로 Android/iOS·토스 동작까지 검증했다고 보고하지 않는다.

## 3. 기술 구성과 저장소

- TypeScript `strict: true`, pnpm workspace, 내부 의존성 `workspace:*`.
- Web/PWA: React·Vite, 앱이 선택한 스타일 체계와 PWA 도구.
- Hybrid Mobile: Ionic React·Capacitor, Android/iOS 네이티브 프로젝트.
- Toss: 설치 버전에 맞는 Apps in Toss SDK와 TDS, 토스 전용 React UI.
- Backend: 프로젝트가 선택한 서버·DB·마이그레이션. Supabase/Edge Functions는 선택지이며 필수 전제가 아니다.
- Test: Vitest·React Testing Library, 필요한 범위의 Playwright·플랫폼 기기 검사.

아래는 목표 구조다. 빈 디렉터리나 선택 플랫폼을 미리 모두 생성할 필요는 없다.

```text
apps/
  web/                 # Web/PWA UI, browser routing and adapters
  mobile/              # Ionic UI, Capacitor adapters, android/, ios/
  toss/                # TDS UI, Toss SDK and platform authentication
  api/                 # Optional backend composition and handlers
packages/
  contracts/           # DTOs, schemas, interfaces and ports
  core/                # Framework-independent domain and use cases
  data/                # Repository implementations and reusable access
  utils/               # Pure general-purpose helpers
  config/              # Shared TypeScript/lint/build presets
scripts/
docs/
  architecture/
  decisions/
```

### 패키지 경계

- `apps/*`는 `packages/*`의 공개 exports로 접근한다. 다른 앱의 소스·컴포넌트·Hook·라우터를 import하지 않는다.
- `contracts`와 `utils`는 앱·플랫폼 SDK에 의존하지 않는다.
- `core`는 contracts·순수 유틸에 의존할 수 있으나 React·Ionic·Capacitor·TDS·구체 DB 클라이언트·브라우저 전역에 의존하지 않는다.
- `data`는 계약을 구현하고 선택한 DB SDK를 사용할 수 있으나 앱을 import하지 않는다.
- 앱 composition root가 저장소·인증·시계·네트워크·기기 어댑터를 업무 로직에 주입한다.
- 패키지 사이 상대 경로로 source를 직접 참조하거나 exports·의존성 선언을 우회하지 않는다. 순환 의존성을 만들지 않는다.

## 4. pnpm·React·의존성 관리

- 설치 전 `package.json`, workspace 설정, lockfile, engines, Node/pnpm 설치 상태를 확인한다.
- 앱별 React·React DOM·타입·라우터 버전은 독립적으로 선택한다. 모든 앱을 같은 React 버전으로 맞추지 않는다.
- TDS·Ionic·라우터의 실제 peer 요구사항을 확인한다. 토스 앱의 React 제약을 PWA·모바일에 전파하지 않는다.
- React를 사용하는 공유 라이브러리를 승인받아 만들 경우 React 중복 번들·peer 선언을 검토한다. core에 React를 넣어 해결하지 않는다.
- 버전 catalog는 공통 도구에 활용할 수 있으나 플랫폼이 요구하는 버전을 무조건 통일하는 장치로 쓰지 않는다.
- 의존성 추가 시 기존 사용 여부·번들 영향·라이선스·유지 상태·플랫폼 호환·버전을 확인한다. 확인하지 않은 SDK API를 가정하지 않는다.
- lockfile의 다른 앱 importer·peer snapshot까지 바뀌면 원인을 검토하고 무관한 변경을 보존/제외한다. 잠금 파일만 통과해도 실제 모듈 연결과 실행은 별도 확인한다.
- 전체 `node_modules` 삭제·강제 재설치·lockfile 재생성을 기본 해결책으로 사용하지 않는다. 개인 PC의 임시 실행 경로를 필수 프로젝트 설정으로 고정하지 않는다.

## 5. Web/PWA

- `apps/web`이 UI·라우팅·브라우저 저장·service worker를 소유한다. PWA 설치는 네이티브 앱 배포와 다르다.
- 서비스 목표에 맞는 반응형 UI와 Safe Area·작은 화면·가로 회전·키보드 접근성을 확인한다.
- 오프라인 지원 작업을 명시한다. API 인증·최초 다운로드·캐시 미적중 기능을 오프라인 가능하다고 안내하지 않는다.
- 캐시 전략은 자산·인증·데이터별로 정한다. 비밀 정보·개인 API 응답을 무분별하게 캐시하지 않는다.
- 업데이트·구버전 캐시·DB 스키마·진행 중 입력의 일관성을 확인한다. 대용량 콘텐츠를 설치 시 전부 precache할지 비용과 필요성을 검토한다.
- PWA 검증은 프로덕션 빌드·설치·새 버전 갱신·온라인/오프라인·캐시 삭제 후 복구를 구분한다.

## 6. Ionic React·Capacitor Hybrid App

- `apps/mobile`이 Ionic 화면·탐색·스타일과 Capacitor 어댑터를 소유한다. Web/PWA URL을 감싼 것만으로 모바일 기능 구현 완료로 보지 않는다.
- core의 규칙은 재사용하되 PWA/Toss 화면·Hook·라우팅을 직접 가져오지 않는다. 메뉴 명칭과 서비스 흐름은 일관되게 유지하고 플랫폼 차이를 기록한다.
- core/CLI/Android/iOS의 호환 버전을 확인한다. 네이티브 플러그인은 모바일 어댑터 뒤에 두고 미지원·권한 거부·취소·오류 처리를 제공한다.
- 앱 ID·표시 이름·아이콘·딥링크·네이티브 버전을 명시적으로 관리한다. 배포 앱 ID를 임의 변경하지 않는다.
- Android는 JDK·SDK·Gradle·Android Studio·target/min SDK·스토어 요구사항을 선택 버전에 맞춰 확인한다. iOS는 macOS·Xcode·서명·플러그인 요구사항을 별도 확인한다.
- 네이티브 프로젝트 소스는 관리하고 복사된 웹 assets·빌드 결과·로컬 SDK 경로·서명 키·개인 환경 파일은 제외한다. 생성 파일 수정이 필요하면 원본과 재생성 영향을 확인한다.
- 운영 앱이 개발 서버·개인 PC·임시 터널을 바라보지 않게 한다. cleartext·임의 도메인 허용·불필요한 권한을 추가하지 않는다.
- 앱 상태 저장·백그라운드/복귀·프로세스 종료·네트워크 전환·Android 뒤로가기·키보드·Safe Area·회전을 실제 환경에서 검사한다.
- 웹 빌드 → Capacitor sync → 네이티브 build → 설치/기기 검증을 각각 기록한다. sync 성공은 APK/AAB/IPA 생성 성공이 아니다.
- Android/iOS가 동시 구현되지 않았다면 지원 상태를 나누어 보고한다.

## 7. Toss Mini App

- `apps/toss`가 TDS UI·토스 SDK·상단 탐색·저장·인증/브리지 통합을 소유한다. 토스 정책과 TDS 기준이 다른 앱과의 외형 일치보다 우선한다.
- SDK·TDS·React·Node 버전과 설정 타입·CLI 명령을 확인한다. 이전 SDK 문서의 파일명·필드를 현재 설정에 임의로 추가하지 않는다.
- 콘솔 appName·유형·카테고리·사용 연령·앱 정보와 실제 기능을 맞춘다. 새 앱 등록 시 인증서·사용자 식별·광고 그룹·API 설정을 다시 검토한다.
- **테스트 Origin과 공개 출시 Origin을 둘 다 확인한다.** 설치 SDK의 공식 도메인 규칙을 검증해 정확한 HTTPS Origin만 허용한다. 와일드카드로 해결하지 않는다.
- Origin으로 앱 인증서를 선택한다면 테스트·출시 양쪽을 동일 앱의 인증서·사용자 네임스페이스로 연결한다. 다른 앱의 인증서·사용자 기록은 격리한다.
- mTLS는 서버에서 처리하고 인증서·개인 키를 앱 번들에 넣지 않는다. 호스팅의 실제 코드 교환 성공을 확인하기 전 지원 가능성을 확정하지 않는다.
- 광고는 실제 발급 운영 ID로 출시한다. 테스트 ID·테스트 보상 경로가 산출물에 남지 않게 검사한다. 생성 제한·발급 대기·광고 없음·미지원·실패를 처리한다.
- 운영하지 않는 광고 기능은 버튼·안내·화면·호출을 함께 제외한다. 클라이언트 완료 이벤트만으로 서버가 실제 시청을 검증했다고 주장하지 않는다.
- 토스 상단 영역·앱 헤더·하단 메뉴·배너·Safe Area·키보드를 제외한 실제 콘텐츠 공간을 처음부터 계산한다. 광고 UI를 자르거나 임의 축소하지 않는다.
- 자동 검사·콘솔 업로드·실기기 테스트·검토 요청·공개 출시를 구분한다. 출시 직후 공개 진입에서도 인증·잔액 등 핵심 API를 재검증한다.
- 업로드 토큰은 사용자 로컬 프로필로 등록하고 읽거나 로그에 남기지 않는다. 업로드와 공개 검토·출시의 승인 범위를 분리한다.

## 8. 공통 UI·데이터·보안 기준

- 고정 영역과 스크롤 영역을 명시하고 중첩 스크롤을 최소화한다. flex 자식의 `min-height: 0`, 앱 셸 높이, 스크롤 전달, 키보드 열린 상태를 확인한다.
- 기능이 같아도 플랫폼별 UI를 독립 구현한다. 접근성 이름·포커스·터치 영역·읽기 순서·오류 복구를 유지한다.
- 로딩·실패·취소·재시도를 처리하고 오류를 조용히 삼키지 않는다. 사용자 메시지는 이해하기 쉽게, 개발 로그는 비밀 정보 없이 남긴다.
- 네트워크·저장 입력을 경계에서 검증한다. 세션·사용자 소유권·보상·한도·권한은 서버에서 검증한다.
- 재시도 가능한 쓰기·보상·결제는 요청 ID와 서버 멱등성을 설계한다. 응답 유실을 실패 확정으로 간주해 새 ID로 중복 처리하지 않는다.
- DB 변경은 마이그레이션으로 관리하고 클라이언트 접근 테이블의 RLS/권한을 검토한다. service role·서버 비밀 키를 프런트에 넣지 않는다.
- 플랫폼별 인증 초기화·세션·저장 namespace를 분리한다. 사용자 삭제·앱 재등록 시 기록 자동 이전·병합을 가정하지 않는다.
- 환경 예시는 placeholder만 사용하고 비공개 `.env`, 키, 토큰, 인증서, 고객 데이터를 커밋하지 않는다. 공개 설정과 비밀 정보를 구분한다.
- 콘텐츠·폰트·이미지·음원의 제작 경위·이용 권한을 확인한다. AI 생성 여부만으로 권리 문제가 해결됐다고 단정하지 않는다.
- 무료 요금제의 실행·호출량·전송량 한계를 확인한다. rate limit이 이미 도달한 유료/무료 호출량 집계를 없앤다고 가정하지 않는다.

## 9. AI 작업 절차·승인

1. 루트와 관련 하위 `AGENTS.md`, 요구사항·진행 기록을 읽고 작업 트리와 기존 변경을 확인한다.
2. 요청 기능·대상 플랫폼·완료 기준을 파악하고 공유 패키지/앱 소유권에 맞게 위치를 정한다.
3. 기존 구현·설치 API·실제 scripts를 확인한다. 큰 변경은 영향과 작업 범위를 먼저 설명한다.
4. 최소 변경으로 구현하고 업무 규칙·버그 회귀에 필요한 테스트를 갱신한다.
5. 관련 검사·diff 검토를 진행하고 결과·미검증·후속 작업을 문서에 기록한다.
6. 변경 요약·수정 파일·실행한 검증·남은 항목을 한국어로 보고한다.

- 사용자 편집·무관한 파일·이력을 덮어쓰지 않는다. 같은 파일의 동시 편집을 피하고 필요한 병렬 작업은 별도 worktree로 격리한다.
- 검색은 `rg`를 우선 사용한다. 실패한 검사를 성공으로 보고하거나 실행하지 않은 명령 결과를 만들지 않는다.
- **커밋·푸시·업로드·배포·공개 출시·운영 DB/설정 변경·자격 증명 교체·데이터 삭제는 명시적 승인을 받는다.** 이미 승인된 범위의 작업에는 같은 승인을 반복 요청하지 않는다.
- force push·hard reset·무차별 clean·사용자 파일 삭제는 별도 승인 없이 실행하지 않는다.
- 승인 요청 전 코드·설정 변경안과 필요한 검사를 준비해 검토 가능한 상태로 만든다. 도구 권한 승인은 별도 절차를 따른다.
- 사용자가 기기 확인을 맡으면 자동 검사까지 진행하고 기기 확인은 대기로 남긴다.
- 프로젝트별 마무리 명령을 추가하려면 승인 범위·예외·커밋 대상·검증·푸시 실패 처리를 명시한다. 다른 프로젝트의 승인 관행을 자동으로 가져오지 않는다.

## 10. 검증 기준과 명령 등록

| 변경 대상 | 필요한 검증 |
| --- | --- |
| core/contracts/utils | 타입·관련 단위 테스트·공개 API·영향 앱 타입 검사 |
| data/backend | 저장소·권한·인증·마이그레이션·멱등성·통합 검사 |
| Web/PWA | 타입·lint·관련 테스트·프로덕션 빌드, 영향 시 설치/캐시/오프라인 |
| Ionic/Capacitor | 타입·웹 빌드·sync·네이티브 빌드·해당 OS 기기 검사 |
| Toss | 타입·lint·관련 테스트·번들·SDK/TDS·광고 검사·토스 실행·공개 Origin 확인 |
| 문서만 변경 | 내용·경로·명령·`git diff --check` |

아래는 형식 예시다. 대상 저장소에 실제 존재하는 package 이름과 scripts로 바꾸고, 없는 명령은 만들기 전 실행 가능하다고 안내하지 않는다. Windows에서 `pnpm.ps1`이 차단되면 `pnpm.cmd`를 사용한다.

```sh
pnpm --filter @<scope>/web typecheck
pnpm --filter @<scope>/web build
pnpm --filter @<scope>/mobile build
pnpm --filter @<scope>/mobile sync:android
pnpm --filter @<scope>/toss build:ait
git diff --check
```

명령마다 통과·실패·미실행과 사유를 기록한다. 같은 코드에서 통과한 검사를 이유 없이 반복하지 않는다. 브라우저·렌더링 테스트를 실제 Android/iOS·토스 검증으로 바꾸어 표현하지 않는다.

## 11. 문서와 인수인계

- **저장소 루트에 `progress.md`를 반드시 생성하고 유지한다.** 기존 파일이 있으면 덮어쓰지 않고 현재 구조에 맞춰 갱신한다. 없으면 첫 작업에서 생성한다.
- `progress.md`에는 날짜·작업 목표·플랫폼별 완료/미완료·변경 파일·실제로 실행한 검사와 결과·미검증 항목·남은 작업을 기록한다. 배포가 있으면 승인 범위·버전·대상·결과도 남긴다. 작업이 끝날 때 이번 변경을 반영하며 실행하지 않은 검증을 완료로 표시하지 않는다.
- 기록 방식은 **상단의 최신 작업 기록 + 하단의 단계별 진행 체크리스트**로 구성한다. 작업 기록 제목은 `## <작업명> (YYYY-MM-DD)`로 하고 최신 작업을 위에 추가한다. 단계별 체크리스트는 실제 완료된 항목만 `[x]`로 표시하고 플랫폼별 준비·구현·자동 검사·기기 검증·출시를 나눈다.
- 각 작업에는 문제/요청, 구현 내용과 주요 파일, 정확한 검증 명령·결과, 남은 경고·미검증·다음 작업을 짧게 기록한다. 사용자 기기 확인은 사용자 보고임을 표시하고 확인한 범위만 반영한다.
- 후속 수정·재검증·배포가 이루어지면 기존 기록을 삭제하지 않고 해당 항목에 `후속 확인`을 추가하거나 새 기록에서 이전 항목을 연결한다. 과거의 ‘미실행/대기’가 최신 상태로 오해되지 않게 적용 전 기록임을 명시한다.
- 승인된 작업과 실제 실행 결과를 구분한다. 업로드·배포가 있으면 대상·앱 버전·deploymentId/커밋 등 식별자·성공 여부를 기록하고 검토 요청·공개 출시·실기기 검증을 별도로 남긴다. 비밀 값·개인 키·토큰은 기록하지 않는다.

`progress.md` 초기 형식 예시:

```markdown
# <프로젝트명> 구현 진행표

## <최신 작업명> (YYYY-MM-DD)

- 요청/문제: <사용자가 요청한 동작 또는 확인한 증상>
- 변경: <플랫폼, 구현 내용, 주요 파일과 역할>
- 검증: `<실제로 실행한 명령>` 통과/실패. <실패 사유·남은 경고>
- 사용자 확인: <기기·환경·확인 범위 또는 확인 대기>
- 적용: <로컬만 변경 / 승인 후 업로드·배포 결과와 식별자>
- 남은 작업: <미검증·후속 조치>

## 단계별 진행 현황

### Phase 1. 공통 기반
- [ ] pnpm workspace·TypeScript·패키지 경계 구성
- [ ] 공통 도메인·계약·업무 규칙과 관련 검사

### Phase 2. Web/PWA
- [ ] 플랫폼 전용 UI·라우팅·데이터 연결
- [ ] 자동 검사·프로덕션 빌드
- [ ] 브라우저·설치·캐시/오프라인 검증 (지원 범위 내)

### Phase 3. Android Hybrid
- [ ] Ionic UI·Capacitor 어댑터·Android 프로젝트
- [ ] 웹 빌드·sync·네이티브 빌드
- [ ] 실제 Android 기기/에뮬레이터 검증

### Phase 4. Toss Mini App
- [ ] TDS UI·토스 인증·테스트/출시 Origin 연결
- [ ] 자동 검사·운영 광고 설정·번들 생성
- [ ] 토스앱 테스트·검토 요청·공개 출시 후 검증

### Phase 5. iOS Hybrid (지원 시)
- [ ] iOS 네이티브 구성·빌드·실제 기기 검증
```

단계 이름·순서는 실제 프로젝트 계획에 맞게 조정한다. 지원하지 않는 플랫폼의 체크리스트를 의무 작업으로 남기지 않는다. 변경이 없는 기존 기록은 불필요하게 다시 작성하지 않는다.
- 요구사항, 구조/의존성, 진행 기록, 플랫폼 README, 운영·배포 절차, 주요 결정을 해당 문서에서 관리한다. 실제 경로를 아래에 등록한다.
- 앱 버전·deploymentId·테스트 링크·배포 대상·확인 날짜와 담당을 기록한다. 옛 기록의 미완료 문구가 최신 상태로 오해되지 않게 한다.
- 장애는 증상·재현 조건·원인 확정 여부·수정·검증·남은 한계를 구분한다. 환경별 결과를 다른 환경에 일반화하지 않는다.
- 비밀 정보와 불필요한 개인 경로·고객 데이터는 인수인계 자료에 넣지 않는다.

## 12. 규칙의 적용

도구·시스템의 안전 규칙을 우선한다. 프로젝트 내에서는 사용자의 명시적 요구, 보안·데이터 무결성, 플랫폼 필수 정책, 아키텍처 경계, 코드 기준 순서로 판단한다. SDK·스토어·광고·요금의 변경 가능한 사실은 공식 자료에서 확인하고 날짜와 검증 범위를 남긴다.
